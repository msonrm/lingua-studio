# 実験計画: LinguaScript に実用的な価値はあるか

## 問い

> 英語という自然言語にどれだけの曖昧さが含まれていて、生成 AI はそれをどれだけ読めるか。
> 十分に読めるなら LinguaScript はおもちゃである。

実用性を示すには「効果がある」だけでは足りず、**代替手段がないこと**を示す必要がある。
この計画は**否定的な結論が出るように**組んである。肯定を探しにいかない。

## 予備調査で分かっていること

ツールが出す英語のうち、どこに曖昧さが残るかを先に確認した。

| 構造 | 英語が区別するか |
|---|---|
| PP の係り先（動詞 vs 名詞） | **しない** — 両方 `I eat an apple in the park.` |
| 否定の作用域（節 vs VP個別） | する — `I do not eat and do not drink.` / `I do not eat and drink.` |
| 等位の位置（VP vs NP） | する — `I eat an apple, and I eat an orange.` / `I eat an apple and an orange.` |
| 等位の入れ子 | する — correlative（both / either）で範囲を明示 |

**良い英語レンダリングそのものが代替手段になっている。** しかも直近の改修
（等位接続の主語繰り返し、correlative）は曖昧さを減らす方向に働いた。

これは LinguaScript の立場を弱める。残る曖昧さの量を測るのが最初の仕事になる。

---

## Phase 0: 曖昧さの棚卸し（LLM 不要）

**やること。** AST を機械的に列挙し、英語にレンダリングし、**同じ英語になる相異なる
AST の組**を集める。

```
AST_a ─┐
       ├─→ "I eat an apple in the park."   ← 衝突
AST_b ─┘
```

衝突する組が、英語では表現し分けられない曖昧さである。**手で選ばない**のが要点で、
「意図した読み」はブロック構造から決まるので後付けできない。

**列挙の範囲。** 無限なので、構造の軸を決めて小さな文型の中で全組み合わせを作る。

- PP の係り先（動詞 / 名詞）
- 等位接続の位置と入れ子（VP / NP × and / or × 2〜3項）
- 否定の作用域（節 / VP個別 / モダリティ）
- 限定詞（all / both / no × 単数 / 複数）
- 時制×相×モダリティ

**出力。** 衝突グループの一覧と、種類別の件数。

**これ自体が「英語にどれだけ曖昧さが含まれているか」への答え**になる
（ただしツールの表現範囲内、という限定付き。この限定は結論に明記する）。

**打ち切り条件A。** 衝突が PP の係り先だけ、あるいは数種類しかない場合、
LinguaScript が解消できる曖昧さは実質1現象しかないことになる。
その時点で「実用性は主張できない」と結論して報告する。

---

## Phase 1: 天井の測定

衝突グループそれぞれについて、**英語だけ**を与えて2つを測る。

| 指標 | 問い | なぜ測るか |
|---|---|---|
| **検出** | この文は曖昧か？ | AI が気づけるなら「聞き返す」で解決する |
| **一致** | どちらの読みか？ | 意図した読みに当たるか |

**打ち切り条件B。** 検出率が高い場合、代替手段(c)「AI が聞き返す」が成立する。
人間が記法を覚える必要がなくなるので、LinguaScript の存在理由が消える。

一致率が最初から高い場合も同様に伸びしろがない。

---

## Phase 2: 代替手段との比較

Phase 1 を通過した場合のみ実施する。**LinguaScript を他の手段と並べて比べる。**

| 条件 | 与えるもの | 何を潰すか |
|---|---|---|
| A | 英語のみ | ベースライン |
| B | 英語 + LinguaScript | 本命 |
| C | LinguaScript のみ | 英語なしで読めるか（「英語ベースだから読めて当然」の検証） |
| D | 曖昧さを解消した英語（言い換え） | **「普通に書き直せばいい」** |
| E | 英語 + 汎用の構造表現（JSON の AST） | **「構造があればよく、この記法である必要はない」** |
| F | 英語のみ + 聞き返してよいと伝える | **「AI が確認すればいい」** |

D・E・F がこの実験の本体である。B が A に勝つのは当たり前で、
**B が D・E・F にも勝たなければ実用性は主張できない。**

---

## Phase 3: 判定（先に決めておく）

結果を見てから基準を決めない。以下を事前に固定する。

| 結果 | 結論 |
|---|---|
| A が最初から高い | **伸びしろなし。** 英語で十分読める |
| F が B と同等 | **不要。** AI が聞き返せば済む |
| D が B と同等以上 | **不要。** 英語を書き直せば済む |
| E が B と同等 | **記法に意味なし。** 構造を与えることが効いているだけ |
| C が低い | 「前提知識なく読める」は成立しない（英語との併用が前提） |
| B のみが有意に高い | **実用性あり。** ここではじめて先へ進む根拠になる |

有意差の扱い: 件数が小さいので統計的検定は行わず、**差が小さければ「差なし」と読む**。
最低でも15ポイント以上の差がなければ差なしとする。

---

## 想定される結論（予測を先に書く）

正直な予測を残しておく。当たっても外れても記録する。

1. 衝突は PP の係り先を中心に**少数**にとどまる（予備調査から）
2. 検出はかなり高い。一致は50%前後（曖昧なので当然）
3. **E（汎用 JSON）が B と同等**になる可能性が高い。効いているのは構造であって記法ではない
4. D（言い換え）も強い。ただし**「言い換えるには曖昧だと気づく必要がある」**ので、
   そこが唯一 LinguaScript 側に残る論点になりうる

4 が示唆する再解釈: **このツールの価値は「曖昧さを符号化する」ではなく
「曖昧さを可視化する」ほうにあるかもしれない。** Phase 0 の衝突一覧はまさにそれで、
LLM に渡すまでもなく成果物になる。

## 実行方法

- `claude -p` CLI（`claude` 2.1.220 が利用可能。API キーは未設定）
- 呼び出しはユーザーのアカウントを消費する
- バッチ実行は避ける方向。複数問題を1回で渡すとモデルが並びからパターンを推測し、
  条件間の比較が汚れる。1問1呼び出しを基本とし、規模は Phase 0 の結果で決める
- 温度・モデルは全条件で固定。条件の提示順はランダム化する
